## Tech Debt

**Generated artifacts live beside source:**
- Issue: `ff-landing/dist/`, `ff-landing/.parcel-cache/`, `ff-landing/node_modules/`, and `ff-landing/bundle.html` exist in the worktree.
- Files: `ff-landing/dist/`, `ff-landing/.parcel-cache/`, `ff-landing/node_modules/`, `ff-landing/bundle.html`.
- Why: likely local build/prototype workflow.
- Impact: It is easy to edit generated output instead of source, or accidentally include large/stale artifacts.
- Fix approach: Treat `ff-landing/src/` as source of truth; regenerate artifacts only via documented scripts.

**Undocumented single-file bundle workflow:**
- Issue: `ff-landing/bundle.html` exists and appears generated by Parcel/html-inline, but `ff-landing/package.json` has no script to reproduce it.
- Files: `ff-landing/bundle.html`, `ff-landing/.parcelrc`, `ff-landing/package.json`.
- Impact: Future agents may not know whether `bundle.html` is canonical, stale, or deployable.
- Fix approach: Add an explicit script such as `build:bundle` if the artifact matters, or remove/ignore it if not.

**Template README is stale:**
- Issue: `ff-landing/README.md` is the default React + TypeScript + Vite template README.
- Impact: It does not explain the app's real purpose, deploy path, or relation to the root product.
- Fix approach: Replace with a short project-specific README.

## Security Considerations

- Risk: Low in current state; no external calls or env usage found.
- Current mitigation: Static UI only.
- Recommendation: If this becomes a real landing/product app, add explicit handling for env vars, analytics consent, and any outbound API calls.

## Performance Bottlenecks

**Large unused UI component inventory:**
- Issue: `ff-landing/src/components/ui/` contains 43 shadcn/Radix component files, while `App.tsx` uses custom inline markup and mostly imports only icons.
- Impact: Vite tree-shaking should avoid unused code in production, but the source tree is heavier than the actual app requires.
- Fix approach: Keep if future UI expansion is planned; otherwise prune unused generated components.

## Fragile Areas

**Mixed build systems:**
- Why fragile: Vite is the declared app build tool, while Parcel/html-inline dependencies and `.parcelrc` also exist.
- Common failures: bundle artifact drifts from Vite output; developers run the wrong build path.
- Safe modification: Document the intended build/deploy workflow before changing build config.
- Test coverage: None.

**Mixed formatting style:**
- Why fragile: `App.tsx` uses semicolons and double quotes; template/shadcn files mix no-semicolon style and single quotes in some config.
- Common failures: noisy diffs if a formatter is introduced later.
- Safe modification: Do not mass-format unless explicitly asked; follow local file style.

## Dependencies at Risk

**Very new major versions:**
- Packages: React 19, Vite 8, TypeScript 6, ESLint 10 in `ff-landing/package.json`.
- Risk: ecosystem/plugin compatibility may be less stable than older LTS-major stacks.
- Impact: install/build/lint may break across environments if versions are not consistently locked by pnpm.
- Fix approach: Use pnpm lockfile consistently; pin or downgrade only if actual incompatibilities appear.

## Missing Critical Features

- Problem: The UI does not connect to the root app's actual FlutterFlow Custom Code Connect pipeline.
- Current workaround: It functions as visual prototype only.
- Blocks: Real landing conversion, auth, checkout, product demo, or generation flow.
- Implementation complexity: Medium to high depending on intended integration.

**No tests:**
- Problem: No test runner or tests in `ff-landing/`.
- Risk: UI behavior can regress silently.
- Priority: Low while prototype-only; medium if it becomes deployable.
